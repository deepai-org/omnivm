# Cross-language type stubs: Python mypy checks calls INTO Rust

OmniVM runs many languages in one program. A function can be **defined in Rust**
and **called from Python**. This example shows the headline feature of the
cross-language stub emitter: a Python team's *existing* mypy type-checks those
cross-boundary calls — the polyglot VM **extends** their typing instead of
discarding it.

## Files

| File             | What it is                                                        |
| ---------------- | ----------------------------------------------------------------- |
| `risk.poly`      | A PolyScript program: two Rust functions called from Python.      |
| `risk.pyi`       | **Generated** Python stub — Rust signatures mapped to Python.     |
| `wrong_call.py`  | Python that calls the Rust functions incorrectly on purpose.      |

## 1. Generate the stub

```bash
# from the repo's polyscript/ directory, after `npm run build`:
node dist/cli-stubs.js ../docs/cross-language-stubs-example/risk.poly --pyi \
  --out ../docs/cross-language-stubs-example/risk
```

This compiles `risk.poly` to a dispatch manifest and emits `risk.pyi`:

```python
# AUTO-GENERATED by PolyScript cross-language stub emitter — DO NOT EDIT.
# Declares functions defined in another OmniVM runtime so that a Python
# type checker (e.g. mypy) can verify calls across the polyglot boundary.

from __future__ import annotations
from typing import Any

# ── defined in Rust ──
def lookup_tier(account_id: int) -> str | None: ...
def score_batch(account_ids: list[int], weight: float, normalize: bool) -> list[float]: ...
```

Note the type mapping the emitter performed on the Rust signatures:

| Rust                       | Python        |
| -------------------------- | ------------- |
| `Vec<i64>`                 | `list[int]`   |
| `f64`                      | `float`       |
| `bool`                     | `bool`        |
| `Vec<f64>` (return)        | `list[float]` |
| `Option<String>` (return)  | `str | None`  |

## 2. mypy catches the mistakes

`wrong_call.py` makes three deliberate errors. Running mypy against the
generated stub:

```bash
mypy wrong_call.py
```

produces (verbatim, mypy 2.1.0):

```
wrong_call.py:18: error: Argument 2 to "score_batch" has incompatible type "str"; expected "float"  [arg-type]
wrong_call.py:23: error: List item 0 has incompatible type "str"; expected "int"  [list-item]
wrong_call.py:23: error: List item 1 has incompatible type "str"; expected "int"  [list-item]
wrong_call.py:29: error: Item "None" of "str | None" has no attribute "upper"  [union-attr]
Found 4 errors in 1 file (checked 1 source file)
```

Each error is a *cross-language* type violation that mypy could never have seen
before — the function bodies are Rust, but their contracts now live in a stub
mypy understands.

## Why this matters

Without the stub, every call into Rust would be untyped `Any`, and these bugs
would only surface at runtime (or as a Rust panic on a bad deserialize). With
the generated `.pyi`, the polyglot boundary is type-checked by the tool the team
already runs in CI.

> If `mypy` is not installed where you read this, the inline comments in
> `wrong_call.py` state the exact diagnostic mypy reports for each line.

A TypeScript/JS guest gets the analogous `.d.ts` (run with `--dts`); `tsc` then
checks calls into the same Rust functions with `number` / `string` / `T[]` /
`T | null` mappings.
